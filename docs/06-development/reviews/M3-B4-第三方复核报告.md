## 2. 错误清单

### L1 事实错误（数字 / 状态 / 文件 / 行为与实测不符）

1. **R44 指错「同源」文件**。原文：「`ImportConfirmService.confirm()` … 把整个文件解析为 `List<List<String>>`（**与 preview 阶段的 `Integer.MAX_VALUE` 同源**）」。
   - 实测：`ImportParseService.PREVIEW_HARD_CAP = 100`；preview（`ImportParseService:160/206`）与 mapping（`ImportMappingService:217`）用的都是 **100**，**不是** `Integer.MAX_VALUE`。
   - 真正同源的是 **validate**：`ImportValidationService.java:157` `parser.parse(file, options, Integer.MAX_VALUE)`。
   - 影响：风险作用域被写窄（只盯 confirm），优化时可能漏改 validate。

2. **R43 把用例数写错**。原文：「现有用例（`ImportConfirmIntegrationTest` **21 项**）未覆盖」。
   - 实测：该类 `@Test` **20 个**（我的正则曾误把 `@Testcontainers` 计入，已用「`^\s*@Test\s*$`」复核），surefire 报告 `tests=20`、`testcase count=20`，20 个方法名逐一列出。
   - 且与同批提交信息「集成测试 26 项」= 20 confirm + 6 query 自洽 ⇒ **21 与自身口径矛盾**。

3. **D1(b) 法律依据误述**。原文：「`MODULE_BOUNDARIES §2.10`（M2-T11 裁定）**要求** `AuditWriteService` 用 `REQUIRES_NEW`，其**目的**是『业务回滚时审计不丢』」。
   - 实测：§2.10 原文目的为「**避免审计失败阻塞业务**」；`git grep REQUIRES_NEW docs/` 显示 §2.10 **未出现 `REQUIRES_NEW`**；`DATABASE_DESIGN.md:1562` 反而给了「**或在业务事务末尾追加**」的等价选项，`:1579` 明确警示避免 `REQUIRES_NEW` 的「部分提交」。

### L2 判断错误（放水 / 过度严格 / 归因跳步）

1. **D2(b) 把偏差方向判反**。项目负责人称实现「记整批行」是「为迁就不变式而扭曲语义」。实际：批次事务整体 ROLLBACK 后，先行行的写入**同样已被撤销**，记为失败才是与 DB 一致；按其字面「只记剩余行」反而制造「既不算成功也不算失败」的空洞。**扭曲语义的是任务书 C2 的字面表述**。

2. **D2(c) 把「范围限制」写成「架构不可达」**。I3 可达：`DATABASE_DESIGN.md:1562` 允许「业务事务末尾追加」，`PURCHASING_WORKFLOW.md:263` 甚至强制采购类审计「同事务、不 `REQUIRES_NEW`」。真实阻因是本批红线「不改 audit 模块」。

3. **D2(a) 忽略已存在的第三种解法**，且与自身裁定自相矛盾：§5.1 裁定 3② 的「批内单事务 + 失败行重放」本身就不依赖 NESTED。
