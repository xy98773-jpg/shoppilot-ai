## 0. 说明

本 ADR 记录一项 **P0（SSOT）级** 文档变更：`DESIGN_BASIS §12.3`「首批必须固化的错误码（索引）」的
**成员资格规则存在不可判定之处**，导致 M2 已实现并依赖的两个认证错误码 `AUTH-1005` / `AUTH-1006`
未被纳入固化清单；本 ADR 明确成员资格规则，并将两码纳入清单。

依据：`ERROR_CODES.md §4.5`（新增错误码流程第 4 步：跨文档事实须「同步 `DESIGN_BASIS.md §12.3` 并记 ADR」）
与 `AGENTS.md §1.2`（冲突按优先级修正低优先级文档并登记 `DESIGN_REVIEW.md`）。

## ADR-002-01：错误码固化清单成员资格规则统一 + 纳入 `AUTH-1005` / `AUTH-1006`

### 背景

- `DESIGN_BASIS §12.3` 声明「固化清单的成员资格以本节为准」，并称 `ERROR_CODES.md` 的 `✅ 已固化` 标记是本节的**派生视图**；
  `ERROR_CODES.md §1.3` 亦有同向表述。两处**方向一致**（本节为成员资格权威）。
- 但 `§12.3` 附注**未给出「一个错误码何时应进入本清单」的可判定规则**，后果是：
  - M2 的 `D-01`（`ADR-001-12`，无状态 JWT）实现**依赖并真栈实测返回** `AUTH-1005`（Access Token 已过期）与 `AUTH-1006`（Refresh Token 无效/已过期）；
  - 两码在 `ERROR_CODES.md §2.2` 有正式定义，但标记为 `➕ 新增`，且**不在** `§12.3` 清单；
  - 按原附注，读者会得出「两码**不该存在**（既非已固化、也不在清单）」的结论——与 M2 实际强依赖的事实矛盾。
- 该缺口曾与下游误用相伴：`USER_ROLES.md`（R25）明确以 `§12.3` 为错误码来源，却把「令牌过期」写成 `AUTH-1001`；
  `ACCEPTANCE_CRITERIA.md §3.3`（R23）亦有同类笔误。**注意**：R26 只主张「清单完整性缺口」，
  **不主张**其为 R23 的根因（R23 的成因已确证为任务书笔误）。

### 可选方案

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A. 只补清单、不动规则 | 在 `§12.3` 追加 `AUTH-1005` / `AUTH-1006` | 治标：规则仍不可判定，下一个新码会再次卡在同一处 |
| B. 补清单 + 明确成员资格规则（**采纳**） | 追加两码，并在附注中给出「纳入条件 / 判定方向 / 变更门槛」 | 治本：把「何时纳入」写成可判定规则，消除同类缺口 |
| C. 改由 `ERROR_CODES.md` 决定成员资格 | 反转权威归属，令 `§12.3` 降为视图 | 与 SSOT 定位冲突（`§12.3` 属 P0，`ERROR_CODES.md` 属 P2），并动摇「索引在 SSOT」的既有约定 |

### 推荐方案（本 ADR 决策）

采用 **方案 B**：

1. **明确成员资格规则**（写入 `§12.3` 附注，唯一权威）：
   - `§12.3` 清单是「已固化」成员资格的**唯一权威来源**；`ERROR_CODES.md` 的 `✅ 已固化` / `➕ 新增` 标记须与本节**逐码一致**。
   - **纳入条件**：凡被**已实现代码**或**已发布里程碑验收项**依赖的错误码，**必须**纳入本节清单；新码一经里程碑实测使用，须在**同一里程碑内**同步纳入。
   - **不一致的处置方向**：以本节成员资格为准，**修正 `ERROR_CODES.md` 的标记**；`✅ 已固化` 标记**不是**纳入依据。
   - **变更门槛**：本节清单增删属 P0，须走 ADR 并登记 `DESIGN_REVIEW.md`。
2. **纳入 `AUTH-1005` / `AUTH-1006`**：在 `§12.3` 清单中紧随 `AUTH-1004` 加入两行。
3. **同步派生视图**：`ERROR_CODES.md §2.2` 中两码标记由 `➕ 新增` 改 `✅ 已固化`。
4. **消解字面重叠（R29）**：收紧 `ERROR_CODES.md §2.2` 的 `AUTH-1001` 含义 / 触发条件措辞，明确其与 `AUTH-1005`（过期）、`AUTH-1011`（非 Bearer）的边界。

### 推荐理由

- **可判定**：把「何时纳入」从隐性约定变为显式规则，杜绝下一次同类缺口。
- **不改权威归属**：仍以 SSOT `§12.3` 为成员资格权威、`ERROR_CODES.md` 为派生视图，与既有约定一致。
- **最小化**：仅新增 2 行清单 + 规则条款 + 2 处标记翻转 + 1 处措辞收紧；不改号码段、不改错误码语义、不改 HTTP 状态。

### 代价与风险

- `§12.3` 属 P0，本变更须在 `DESIGN_REVIEW.md` 留痕（已登记 R26 / R29，状态 ✅）。
- 纳入条件第 2 条对后续里程碑形成**约束**：里程碑内新用的错误码必须当批入清单，否则里程碑验收不予通过。
- `AUTH-1001` 措辞收紧（R29）改变的是 `ERROR_CODES.md` 的**文字表述**（含义 / 触发条件），**不改**错误码本身、HTTP 状态与语义；
  已确认 M2 实现与实测行为与新表述一致（无凭证 → `AUTH-1001`；非 `Bearer` → `AUTH-1011`；过期 → `AUTH-1005`）。

### 未来重新评估的触发条件

- 出现「已实现代码依赖的码无法归入任何 `§12.2` 号码段」——需评审号码段划分。
- 再次发生「本节清单与 `ERROR_CODES.md` 标记不一致」——说明派生视图同步机制仍有漏洞，需评审改为工具化校验。
