## 0. ADR 说明

### 0.1 什么是 ADR

**架构决策记录（ADR）** 是一份**简短、结构化、按时间累积**的文档，用于记录"我们做了什么架构决策、为什么这么做、放弃了哪些方案、代价是什么、什么时候需要重新评估"。

ADR 的核心价值：

1. **可追溯**：后来者能理解"当时为什么这么选"，而不是反复质疑既定方案。
2. **可讨论**：把取舍写清楚，让分歧针对**取舍本身**而不是"感觉"。
3. **可演化**：预先写出"何时重新评估"，使架构演进有触发条件而非拍脑袋。

### 0.2 编号规则

- 格式：`ADR-<三位序号>-<主题>`，如 `ADR-001-ARCHITECTURE`。
- 一份 ADR 内部可包含**多个子决策**，格式 `ADR-<ADR 号>-<两位子号>`，如 `ADR-001-01`。
- 新决策若**替代**某个已有子决策，必须**新增 ADR** 并在被替代者中标注 `Superseded by ADR-00X-YY`，**不直接删除原文**。

### 0.3 状态机

```
Proposed ──(评审通过)──> Accepted ──(被新决策取代)──> Superseded
    │                          │
    └──(否决/撤回)──> Rejected  └──(不再适用)──> Deprecated
```

| 状态 | 含义 |
| --- | --- |
| `Proposed` | 已提出，待评审确认 |
| `Accepted` | 已评审通过，成为约束 |
| `Superseded` | 已被更新的 ADR 取代（保留原文以便追溯） |
| `Rejected` | 曾被提出但被否决 |
| `Deprecated` | 曾生效但已不再适用（无替代决策） |

> **本 ADR 整体状态为 `Proposed`**：其结论已作为 M0 设计基线写入各设计文档，但**仍需在 M1 启动前一并经项目负责人评审确认**。确认后整体转为 `Accepted`（个别待确认项除外）。

### 0.4 本 ADR 的范围

- 覆盖 **`ADR-001-01` ~ `ADR-001-15` 共 15 个决策**，涉及：系统形态、语言与职责划分、AI 服务边界、计算方式、依赖引入与否、一致性保障、持久层、状态存储、认证、精度、表设计分离、Python 编排形态。
- **不含**：具体表字段（见 `docs/02-database/*`）、具体 API（见 `docs/03-api/*`）、技术版本细节（见 `TECH_STACK.md`）。
- **约束来源**：全部决策必须服从 `DESIGN_BASIS.md`（SSOT）；若本 ADR 与 SSOT 冲突，**以 SSOT 为准**并提交变更请求。

### 0.5 重要声明

> **本 ADR 的决策不是不可更改的事实。** 任何变更都需要：

## ADR-001-01：为何选择模块化单体（Modular Monolith）而不是微服务

**状态**：Proposed

### 背景

ShopPilot AI 是一款面向小型电商团队的库存决策与采购协同平台，首期由小团队开发。业务天然可分为身份、资料、导入、库存、销售、分析、补货、采购、审计等边界（`DESIGN_BASIS.md §7.1` 已定义 10 个 Java 模块）。

关键疑问：**是否应该在首期就拆分为微服务？**

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 单个大泥球单体** | 全部代码在一个无边界的大工程里，模块划分仅在目录层面 |
| **B. 模块化单体**（推荐） | 一个部署单元内划分 10 个**强边界模块**，依赖方向强制、跨模块只经 `application` 层接口 |
| **C. 微服务** | 按业务域拆成独立服务，独立部署、独立数据库 |
| **D. 服务网格 / 事件驱动微服务** | 微服务 + MQ + 服务注册中心 + 分布式事务 |

### 推荐方案

**方案 B：模块化单体**。

- 单个 Spring Boot 部署单元（`backend-java`），内部 10 个 Maven 子模块。
- 模块边界通过 **`pom.xml` 依赖声明 + 代码评审检查清单**（`MODULE_BOUNDARIES.md §9`）强制。
- 模块间只允许经对方 `application` 层服务接口调用；单库单事务。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **首期目标是"快速形成闭环"**，而非承载超大流量；微服务的分布式复杂度（网络、序列化、一致性、可观测性）远超收益 | `PRD.md §3.1` 闭环定义 |
| 2 | **SSOT 已明确**"采用模块化单体（10 个模块），保留拆分可能但不提前支付分布式成本" | `DESIGN_BASIS.md §2.1`、`§7.1` |
| 3 | **一致性依赖单库本地事务**（`ADR-001-09`）：库存、采购、到货的一致性用本地事务即可保证；微服务会让这些变成分布式事务 | `DATABASE_CONSTRAINTS.md §7` |
| 4 | **团队规模小**：微服务需要独立的 CI/CD、部署、监控、on-call 能力，小团队无力承担 | `PRD.md §2`（小团队画像） |
| 5 | **边界已经清晰**：10 个模块的依赖方向是被强制执行的有向无环图，未来若需拆分已有天然缝线 | `MODULE_BOUNDARIES.md §1` |
| 6 | **单机 Docker Compose 部署足够**（明确不做 K8s） | `DESIGN_BASIS.md §2.1` |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 单点发布 | 任一模块变更需整体重新部署 | 首期可接受（小团队）；CI 快速构建 |
| 模块边界靠纪律 | 缺乏网络/进程隔离，越界靠评审发现 | `MODULE_BOUNDARIES.md §9` 检查清单 + 依赖方向在 POM 中显式声明 |
| 横向扩展受限 | 只能整体扩容 | 首期数据量与并发量小，无此需求 |
| 编译期耦合风险 | 若有人打破方向，会形成隐性耦合 | CI 可加"依赖方向静态检查"（计划在 M7 评估） |

### 未来重新评估的触发条件

- 出现**单一模块的性能瓶颈**且整体扩容无法解决；
- 团队规模显著扩大（出现多个并行开发小组且发布节奏冲突）；
- 需要**独立部署与独立扩缩容**的强诉求出现；
- 单库达到**分库分表或独立数据源**的必要性；
- 需要**跨团队独立技术栈**。

## ADR-001-02：为何用 Java 作为核心业务服务（而非全 Python）

**状态**：Proposed

### 背景

项目同时包含 Java 与 Python 两种技术栈。需要明确：**核心业务（身份、资料、库存、采购、账务性状态机）由谁承载？**

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 全 Java** | 业务 + 分析 + LLM 编排全用 Java |
| **B. 全 Python** | 业务 + 分析 + LLM 编排全用 Python（FastAPI + SQLAlchemy） |
| **C. Java 承载业务 + Python 承载 AI 分析**（推荐） | Java 负责全部业务写操作与状态机，Python 负责统计/AI 计算 |

### 推荐方案

**方案 C**。Java 作为**核心业务服务**，是所有业务写操作的唯一入口与状态的唯一权威（`DESIGN_BASIS.md §13.2`）。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **业务需要强事务与状态机**：库存/采购/到货的一致性依赖本地事务、乐观锁、状态守卫式 UPDATE；Java + Spring 的事务与 MyBatis-Plus 的租户插件是 SSOT 已选定的组合 | `DESIGN_BASIS.md §6 第 4 条`、`DATABASE_CONSTRAINTS.md §7` |
| 2 | **精确数值语义**：金额/数量用 `BigDecimal`；Java 在企业级账务/事务场景的成熟度高于 Python Web 栈 | `DESIGN_BASIS.md §14.2` |
| 3 | **团队协作与类型安全**：`Spring Boot + Spring Security` 提供成熟的认证授权、统一异常、校验、报表与运维生态 | `TECH_STACK.md §1.2` |
| 4 | **Python 的强项在数据/统计/AI**，不在事务性业务；让 Python 写业务库会破坏"状态唯一权威"（`ADR-001-04`） | `DESIGN_BASIS.md §13.2` |
| 5 | **权限与隔离在 Java 侧统一实现**（`TeamContext` + 租户插件 + 权限切面），避免双处实现 | `MODULE_BOUNDARIES.md §6` |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 双语言维护成本 | 需维护 Java 与 Python 两套工程与依赖 | 明确各自边界；Python 只做无状态计算 |
| 跨语言契约风险 | 契约不一致会导致集成缺陷 | `AI_SERVICE_CONTRACT.md` + 契约测试 + 精度约定（`§14.2`） |
| Java 内存与启动开销 | 相比 Python 更重 | 首期规模小，可接受 |

### 未来重新评估的触发条件

- 业务中出现**大量以数据科学为核心的新能力**且 Java 侧实现成本极高；
- Java 侧出现**难以解决的性能瓶颈**且与语言强相关；
- 团队技术栈发生根本性变化（如全面转向 Python 团队）；
- 出现了 **Java 与 Python 双向写业务库**的合理需求（当前被认为必须避免）。

## ADR-001-03：为何用 Python 作为 AI 分析服务（而非全 Java 或用大数据平台）

**状态**：Proposed

### 背景

分析服务需要完成：数据质量校验、移动平均与 3σ 截尾、波动率、风险规则、补货计算、Prompt 组装与 LLM 调用。需确定承载语言与平台。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 全 Java** | 用 Java 实现统计分析并与 LLM 交互 |
| **B. Python 微服务/分析服务**（推荐） | FastAPI + Pydantic + pandas，作为独立内部服务 |
| **C. 大数据平台** | Spark/Flink + 数据仓库 + 调度平台 |
| **D. 直接在 Java 内嵌脚本引擎** | 用 JSR-223 / GraalVM 内嵌 Python |

### 推荐方案

**方案 B**：独立的 Python AI 分析服务（`service-ai`），8 个内部模块（`DESIGN_BASIS.md §7.2`），**不暴露公网**。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **生态成熟**：pandas 在统计计算、缺失值处理上生态完善；FastAPI + Pydantic v2 提供强校验与自动 OpenAPI | `TECH_STACK.md §1.3` |
| 2 | **LLM 生态以 Python 为主**：OpenAI 兼容 SDK、Prompt 工具链在 Python 侧最丰富 | `TECH_STACK.md §1.3.1` |
| 3 | **计算与业务解耦**：分析是**无状态纯计算**，天然适合独立服务；失败可降级而不影响主链路 | `DESIGN_BASIS.md §9.7` |
| 4 | **大数据平台过重**：首期单次分析上限 2000 SKU、数据量小，引入 Spark/数据仓库的运维成本远超收益 | `DESIGN_BASIS.md §10.6`（`MAX_ANALYSIS_SKUS=2000`） |
| 5 | **内嵌脚本不可控**：GraalVM 内嵌 Python 会带来工具链、版本与调试复杂度，收益低 | — |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 跨语言数值一致性 | pandas 默认 `float`，与 Java `BigDecimal` 语义不同 | 进入计算层前转 `Decimal`，输出前按 `§14.2` 量化；契约测试比对 |
| 额外部署单元 | 需单独构建、部署与监控 | 仅内网暴露；健康检查与日志统一 |
| 服务间通信成本 | HTTP 调用与序列化开销 | 首期数据量小；异步任务 + 状态轮询 |
| Python 生态版本敏感 | 依赖升级可能破坏兼容 | 精确版本锁定（`requirements.txt`） |

### 未来重新评估的触发条件

- 分析数据量或 SKU 规模**远超** `MAX_ANALYSIS_SKUS`，单机 pandas 无法满足；
- 需要**分布式计算 / 数据仓库**（如引入多源大数据分析）；
- Java 生态出现**成熟的、等价的统计与 LLM 工具链**且维护成本更低；
- Python 服务的运维成本成为主要负担。

## ADR-001-04：为何 AI 服务不直接写业务数据库

**状态**：Proposed

### 背景

分析结果需要落库（`analysis_items` / `replenishment_items`）。疑问：**是否应让 Python 直接写数据库以提高效率、减少一次网络往返？**

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. Python 直连业务库并写结果** | Python 持有数据库连接，直接写 `analysis_items` |
| **B. Python 只返回 JSON，Java 校验后落库**（推荐） | Python 返回结构化结果，Java 校验、补齐业务字段、落库 |
| **C. Python 写独立的"分析库"，再由同步任务搬到业务库** | 双库 + 数据同步 |

### 推荐方案

**方案 B**：**Python 不持有任何业务数据库连接**，只返回 JSON；由 Java 完成校验与持久化。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **状态唯一权威**：`analysis_run_id` 由 Java 生成，业务状态由 Java 权威，结果持久化由 Java 完成——避免双写状态 | `DESIGN_BASIS.md §13.2` |
| 2 | **权限与隔离只在 Java 侧**：Python 不感知权限；若 Python 直写，则必须复制全套租户隔离与权限逻辑，极易出错 | `MODULE_BOUNDARIES.md §7.2` |
| 3 | **数据校验在 Java 侧收口**：Python 返回结果必须经 Java 二次校验（不符 → `ANL-7004` 且不落库） | `DESIGN_BASIS.md §12.3` |
| 4 | **最小权限原则**：Python 不持有业务库凭据，降低误写/越权风险 | `SYSTEM_ARCHITECTURE.md §调用与写入边界` |
| 5 | **避免双库同步复杂度**：方案 C 引入数据同步与一致性窗口，收益不匹配 | — |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 大数据量结果传输 | 结果经 HTTP 传输，体积可能较大 | 分页/分批返回；单次上限 2000 SKU |
| 落库成为 Java 侧负担 | 大批量写入集中在 Java | 按批事务（≤500 行）落库 |
| 校验逻辑需在两端保持一致 | 契约漂移风险 | `ANALYSIS_CONTRACT.md` + 契约测试 |

### 未来重新评估的触发条件

- 分析结果体量增长到**HTTP 传输成为瓶颈**；
- 出现**必须由 Python 侧持久化的中间态**（如超大规模中间结果）；
- 架构演进为**独立分析数据仓库**且需要专用账号与隔离；
- 引入事件驱动（MQ）后，落库职责重新划分。

## ADR-001-05：为何首期采用规则计算 + 移动平均而非 ML 模型

**状态**：Proposed

### 背景

补货决策的核心是"日均销量 `D`"与"风险识别"。可选：机器学习时间序列模型（LSTM/Prophet/XGBoost）或确定性统计方法。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 确定性移动平均 + 3σ 截尾 + 规则引擎**（推荐） | `avg-ma-3sigma-v1`，6 条确定性风险规则 |
| **B. 统计时间序列模型**（Prophet / ARIMA） | 可捕捉季节性/趋势 |
| **C. 深度学习**（LSTM / Transformer） | 可捕捉复杂模式 |
| **D. 混合**（规则 + ML，ML 仅做参考） | 规则为主，ML 提供辅助分 |

### 推荐方案

**方案 A**：首期用确定性方法（`DESIGN_BASIS.md §10.1` 的 `avg-ma-3sigma-v1` 与 `§11` 的 6 条规则）。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **可解释性**：每条建议都必须能回答"当时为什么这么算"；移动平均与规则可逐项展开 | `PRD.md §3.3`、`DESIGN_BASIS.md §3.1` |
| 2 | **可测试性**：确定性算法可以用 golden cases 与边界用例精确断言 | `TEST_STRATEGY.md §11` |
| 3 | **数据量不足**：小团队历史数据质量与长度不足以训练可靠模型 | `DESIGN_BASIS.md §2.1`、`PRD.md §8` |
| 4 | **建立信任**：先让人工能理解与核对，再逐步引入复杂模型 | `PRD.md §1`（P-2/P-3） |
| 5 | **SSOT 已明确**：Out of Scope 明确"机器学习时间序列预测模型（LSTM/Prophet 等）" | `DESIGN_BASIS.md §2.1` |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 准确性有限 | 无法处理季节性、促销、趋势 | 明确不做（`§2.1`）；用 `SALES_ANOMALY` 提示异常，不猜测 |
| 促销期误判 | 大促销量异常会干扰 `D` | 3σ 截尾 + `SALES_ANOMALY` 提示；不做促销修正（`§11.2`） |
| 竞争劣势 | 相比有 ML 的产品预测弱 | 首期以"可解释 + 闭环"为差异化，而非预测精度 |

### 未来重新评估的触发条件

- 积累到**足够长度与质量的历史数据**（如 ≥1–2 年且含促销标注）；
- 客户对**预测精度**提出明确需求且愿提供数据；
- 出现**可解释性与可测试性兼顾**的模型方案（如带解释的统计模型）；
- 现有规则在真实场景中**系统性失效**且有可量化的改进目标。

## ADR-001-06：是否需要 LangGraph

**状态**：Proposed

### 背景

分析流程包含多个步骤（数据质量 → 统计 → 风险规则 → 补货计算 → LLM 解释）。LangGraph/LangChain 提供了"图式编排 + 工具调用 + 状态管理"的能力。疑问：是否应引入？

| --- | --- |

| **D. 自研通用工作流引擎** | 自建 DAG 引擎 |

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **流程是线性的、确定的**：`validate → stats → rules → replenishment → llm`，无复杂分支或循环 | `PROJECT_STRUCTURE.md §5` |
| 2 | **可控与可测**：显式编排的行为完全可预测，便于写 golden cases 与排障；框架抽象会掩盖实际行为 | `DESIGN_BASIS.md §7.2 注` |

| 5 | **依赖越少越好**：框架会带来版本漂移与调试复杂度；首期收益低 | `TECH_STACK.md §2` |

| 代价/风险 | 说明 | 缓解 |

- 分析流程出现**多分支、多循环、条件重试**的复杂控制流；

- LangGraph 生态成熟到**显著降低**维护成本且其可观测性能满足排障需求。

## ADR-001-07：是否需要 Redis

**状态**：Proposed

### 背景

常见场景会想到 Redis：会话、缓存、分布式锁、任务队列、限流。需逐项判断本项目是否真的需要。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 不引入 Redis**（推荐） | 用 MySQL + HTTP 轮询 + 本地事务替代全部候选用途 |
| **B. 引入 Redis 做会话与缓存** | Session 存储 + 业务缓存 |
| **C. 引入 Redis 做分布式锁与队列** | 锁 + Celery/RQ 队列 |
| **D. 引入 Redis 作为全方位基础设施** | 上述全部 |

### 推荐方案

**方案 A：不引入 Redis**（与待决策 `DESIGN_BASIS §15 D-07` 的推荐一致）。

### 逐项排除候选用途

| 候选用途 | 是否需要 | 替代方案 | 依据 |
| --- | --- | --- | --- |
| **会话（Session）** | ❌ 不需要 | 采用无状态 JWT（`ADR-001-12`），服务端不存会话 → 无需 Redis 存 Session | 待决策 `D-01`、`D-07` |
| **缓存** | ❌ 不需要 | 首期数据量小（单团队数千 SKU）；列表接口通过**索引优化**（`team_id` 最左）满足 p95 < 500ms，不依赖缓存 | `NFR-PERF-01`、`DATABASE_CONSTRAINTS.md §3` |
| **分布式锁** | ❌ 不需要 | 单实例部署 + **单库本地事务**；并发控制用**唯一约束 / 乐观锁 / 状态守卫**（等价 CAS），无需跨节点锁 | `DATABASE_CONSTRAINTS.md §7.2` |
| **任务队列** | ❌ 不需要 | 异步分析用 **HTTP + 状态轮询**（Java 发起、Python `BackgroundTasks`/线程池执行），无 MQ | `DESIGN_BASIS.md §13.1`、`ADR-001-08` |
| **限流** | ❌ 不需要 | 单团队规模、内部系统；如需限流可在网关（nginx）层做简单限制；首期不做分布式限流 | — |

### 推荐理由

| # | 理由 |
| --- | --- |
| 1 | **零新增运维组件**：少一个需要部署、监控、备份、排障的中间件 |
| 2 | **一致性更简单**：所有关键写操作都在**同一本地事务**内完成，无需分布式锁与缓存一致性维护 |
| 3 | **SSOT 已明确不引入**：`§2.1` Out of Scope、待决策 `D-07` 推荐"首期不引入" |
| 4 | **用数据库能力替代**：唯一约束、乐观锁、状态守卫、复合索引已覆盖 Redis 的候选用途 |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 无缓存时的读压力 | 高并发读会打到 MySQL | 首期并发低；索引保证查询高效；必要时再评估缓存 |
| 无分布式锁 | 未来多实例部署时并发控制需重新设计 | 当前单实例；并发约束已下沉到 DB 层（唯一约束/状态守卫），多实例仍成立 |
| 登出即时失效受限 | 无状态 JWT 天然难以即时失效 | 用短 Access TTL + Refresh 撤销表（`D-01`），必要时评估黑名单（不建议首期引入） |

### 未来重新评估的触发条件

- **多实例部署**导致内存状态/local 锁不再足够（但 DB 级约束仍有效）；
- 读请求量导致**数据库成为瓶颈**且索引优化无法解决；
- 需要**跨服务分布式锁**或**真正的任务队列语义**（延迟、重试、死信）；
- 需要**限流/熔断**等网关级能力且 nginx 无法满足；
- 引入 MQ 后需要 Redis 作为其配套。

## ADR-001-08：分析任务的状态与失败恢复

**状态**：Proposed

### 背景

分析是**异步任务**（默认 `timeout_at` 300s，见 `DESIGN_BASIS.md §13.4`），存在"任务卡住""LLM 失败""服务重启"等失败场景。需要明确：状态归谁、如何恢复、如何降级。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. Java 权威状态 + 轮询 + `timeout_at` 兜底 + `DEGRADED` 降级**（推荐） | Java 持有业务状态，轮询 Python 进度，超时兜底 |
| **B. 引入 MQ（Kafka/RabbitMQ）** | 用消息驱动任务，消费方回调 |
| **C. Python 写状态到业务库** | Python 直接维护任务状态 |
| **D. 全同步执行** | 请求内同步等待分析完成 |

### 推荐方案

**方案 A**。

### 推荐理由与机制

| 机制 | 说明 | 依据 |
| --- | --- | --- |
| **Java 权威状态** | `analysis_runs.status`（`AnalysisRunStatus`）由 Java 唯一维护；Python 侧状态仅为执行细节 | `DESIGN_BASIS.md §13.2` |
| **轮询** | Java 通过 `GET /internal/v1/analysis/runs/{id}` 轮询进度（`§13.4`：超时 3s，重试 1 次）；前端 2s→10s 指数退避轮询 | `§13.1`、`NFR-PERF-05` |
| **`timeout_at` 兜底** | 超过 `timeout_at` 仍为 `RUNNING` 的任务，由系统级扫描置为 `TIMEOUT`（用 `idx_run_timeout`） | `§9.7`、`DATABASE_CONSTRAINTS.md §3.3` |
| **`DEGRADED` 降级** | 规则计算成功但 LLM 失败/超时/校验失败 → `DEGRADED`（终态，业务可用），`llm_status` 记录原因 | `§9.7`、`§9.8` |
| **失败可重试** | 不自动重试；用户发起新 run（生成新 `run_id`） | `§13.4` |
| **状态守卫** | 状态推进用条件 UPDATE（`WHERE status = 旧值`），终态不可变 | `DATABASE_CONSTRAINTS.md §7.2` |

**为何不用 MQ（方案 B）**：首期异步分析用 HTTP + 状态轮询即可满足；引入 MQ 增加部署、幂等、顺序处理与排障复杂度，收益不匹配（`§13.1`、`§2.1`）。

**为何 Python 状态不落业务库（方案 C）**：详见 `ADR-001-04`；双写状态会导致不一致与权限/隔离逻辑复制。

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 轮询开销 | 频繁轮询增加请求量 | 指数退避（2s→10s）；状态查询走索引 |
| 无事件驱动实时性 | 状态变更非即时通知 | 首期实时性要求低；退避轮询足够 |
| `RUNNING` 悬挂 | Python 崩溃后任务可能长期 `RUNNING` | `timeout_at` 系统级扫描兜底 |
| 结果丢失风险 | Python 完成但 Java 未取到结果 | Java 可重新拉取状态与结果；落库幂等（`uk_ai_run_sku_wh`） |
| 无自动重试 | 失败需人工重发 | 明确设计（`§13.4`）；前端提供"重新分析"入口 |

### 未来重新评估的触发条件

- 分析任务量或并发量**显著上升**，轮询成为负担；
- 需要**实时进度推送**（如 WebSocket）或**任务优先级/调度**；
- 需要**跨服务可靠投递与死信**（此时评估 MQ）；
- 引入 MQ 后重估"状态权威"与幂等策略。

## ADR-001-09：如何保证库存、采购与到货的一致性

**状态**：Proposed

### 背景

库存余额、库存流水、采购单、到货单之间必须严格一致：**余额必须能由流水推导**、`received_qty ≤ ordered_qty`、**只有确认到货才入库**。这是本项目最核心的正确性要求。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 单库本地事务 + 幂等键 + 状态守卫 + 乐观锁/行锁 + 余额由流水推导 + 对账校验**（推荐） | 全部一致性用 DB 事务与约束表达 |
| **B. 分布式事务（2PC/TCC/Saga）** | 跨服务一致性 |
| **C. 事件驱动最终一致（MQ + 补偿）** | 通过事件与补偿达成最终一致 |
| **D. 定时批处理重算余额** | 定期全量重算 |

### 推荐方案

**方案 A**，六层机制叠加：

| # | 机制 | 说明 | 依据 |
| --- | --- | --- | --- |
| 1 | **单库本地事务** | 余额与流水**同事务**写入；采购/到货跨模块调用复用外层事务（`REQUIRED`） | `MODULE_BOUNDARIES.md §2.5/§2.9` |
| 2 | **幂等键** | 库存流水 `(team_id, idempotency_key)`、采购单/到货单幂等键唯一约束；到货单幂等键 **`NOT NULL`**（收货不可逆） | `DATABASE_CONSTRAINTS.md §2.2` |
| 3 | **状态守卫（等价 CAS）** | 状态推进用条件 UPDATE（`WHERE status = 旧值`）；如"建议 `APPROVED → CONVERTED`"用状态 + `version` 守卫，把"一条建议只能转一次"变成 DB 可判定事实 | `DATABASE_CONSTRAINTS.md §2.2 幂等 4` |
| 4 | **乐观锁 / 行锁** | 余额更新用乐观锁 `version`（冲突 `INV-5002`，重试 3 次）；`poi.received_qty` 累加用 `SELECT ... FOR UPDATE`（防丢失更新） | `DATABASE_CONSTRAINTS.md §7.1` |
| 5 | **余额由流水推导** | `inventory_balances.on_hand_qty` 是流水的累加结果；DB `CHECK (qty_after = qty_before + qty_delta)` 让流水自证 | `DESIGN_BASIS.md §3.1 第 4 条` |
| 6 | **对账校验** | 对账 SQL 断言 `Σ qty_delta == on_hand_qty`，返回 0 行；每日巡检 | `TEST_STRATEGY.md §7.3` |

**库存唯一写入口**：所有库存变更**必须**经 `InventoryWriteService`（`MODULE_BOUNDARIES.md §2.5`），禁止任何模块直接 `UPDATE inventory_balances`。

### 推荐理由

| # | 理由 |
| --- | --- |
| 1 | **一致性可以用"单库 + 约束"直接表达**，无需分布式事务的复杂度 |
| 2 | **DB 层成为最后防线**：即使应用层有 bug，唯一约束/`CHECK`/非负约束仍能兜底 |
| 3 | **可测试**：并发、幂等、回滚都有明确的期望（`DATABASE_CONSTRAINTS.md §8.5/§8.6`） |
| 4 | **简单可运维**：无 MQ、无分布式事务协调者、无补偿任务 |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 单库写入压力 | 所有写集中在一个库 | 首期规模小；按批事务、缩短事务时长（单事务 < 100ms 量级） |
| 跨模块长事务 | 到货确认涉及多模块写入 | 事务内禁用远程调用；明确事务传播 |
| 乐观锁重试 | 高冲突下重试增加延迟 | 重试 3 次（20/50/120ms）；冲突高时改用悲观锁 |
| 对账为周期性 | 不保证实时发现不一致 | `CHECK` 约束实时兜底 + 每日对账巡检 |

### 未来重新评估的触发条件

- 数据库**分库分表**或跨库写入成为必需；
- 出现**跨服务事务**（如拆分采购/库存为独立服务）；
- 引入 MQ 后采用**最终一致 + 补偿**模型；
- 单库写入成为性能瓶颈且无法通过索引/批处理解决。

## ADR-001-10：持久层选择 MyBatis-Plus 而非 JPA

**状态**：Proposed

### 背景

持久层可选 MyBatis-Plus / Spring Data JPA / 原生 MyBatis。本项目需要**团队隔离兜底**、**复杂聚合查询**、**批量导入性能**。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. MyBatis-Plus**（推荐） | `mybatis-plus-spring-boot3-starter` + `TenantLineInnerInterceptor` |
| **B. Spring Data JPA / Hibernate** | 隐式 SQL、脏检查、延迟加载 |
| **C. 原生 MyBatis + XML** | 纯 MyBatis，无 Plus 增强 |
| **D. jOOQ** | 类型安全 SQL DSL |

### 推荐方案

**方案 A：MyBatis-Plus**（SSOT 已选定，`DESIGN_BASIS.md §6 第 4 条`明确要求租户插件）。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **SQL 透明可控**：便于按 `team_id` 最左索引优化；复杂统计/聚合直接手写 SQL 更清晰 | `DATABASE_CONSTRAINTS.md §3.1` |
| 2 | **团队隔离兜底**：`TenantLineInnerInterceptor` 自动追加 `team_id`，正是 SSOT 指定的兜底方案 | `§6 第 4 条` |
| 3 | **枚举存储贴合**：与"枚举以 `VARCHAR(32)` 存大写字符串 + `CHECK`"完全契合（自定义 `TypeHandler`） | `§4.1` |
| 4 | **批量导入性能可控**：原生批量 `insert`/`update` 便于满足"1 万行 < 60s" | `NFR-PERF-02` |
| 5 | **无隐式懒加载 / N+1**：避免 JPA 常见的性能陷阱，行为可预测 | `TECH_STACK.md §1.2.2` |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 手写映射与 SQL | 需要手动维护字段映射，重复劳动 | 代码生成/Mapper 约定；DTO 与实体分离（`CODING_STANDARDS.md §3.9`） |
| 无自动 DDL | 表结构需 Flyway 维护 | 明确用 Flyway（`CODING_STANDARDS.md §6`） |
| 复杂关联需手写 | 无法像 JPA 一样自动关联 | 首期查询以聚合为主，手写更可控 |
| 团队隔离"看似自动" | 插件有盲区（原生 SQL、别名、UNION） | **业务层仍须显式同团队校验**（双保险） |

### 未来重新评估的触发条件

- 出现**极其复杂的对象图持久化**需求且 JPA 明显更合适；
- MyBatis-Plus 与 Spring Boot 版本**starter 不兼容**且长期无解；
- 团队整体技术栈转向 JPA 且愿承担学习与陷阱成本；
- 需要**跨数据库方言**支持（当前锁定 MySQL）。

## ADR-001-11：状态字段用可读字符串枚举而非 TINYINT

**状态**：Proposed

### 背景

状态字段（如 `analysis_runs.status`、`purchase_orders.status`）可以存 `TINYINT` 数字或字符串。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. `VARCHAR(32)` 存大写常量字符串 + 应用层枚举 + DB `CHECK`**（推荐） | 如 `status = 'RUNNING'` |
| **B. `TINYINT` 数字 + 字典表/枚举映射** | 如 `status = 2` |
| **C. MySQL 原生 `ENUM` 类型** | 数据库级枚举，但改动需 ALTER |
| **D. 独立字典表 + 外键** | 状态存 ID 关联字典表 |

### 推荐方案

**方案 A**（SSOT 已定，`DESIGN_BASIS.md §4.1` 明确"所有枚举只在此处定义一次""枚举值为大写字符串，直接存入数据库"）。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **可读、调试友好**：直接查库即可看懂状态，无需对照字典 | `§4.1` |
| 2 | **扩展无需改列定义**：新增枚举值只需改 `CHECK` 约束（或迁移），不必重新分配数字含义 | `§4.1` |
| 3 | **与 SSOT 单一来源契合**：`§9` 是枚举唯一定义处，字符串与文档逐字符一致 | `§9` |
| 4 | **DB 可兜底**：MySQL 8.0.16+ 的 `CHECK` 约束保证取值合法性；不存魔法数字避免"猜数字" | `DATABASE_CONSTRAINTS.md §4.1` |
| 5 | **避免原生 `ENUM` 的迁移痛点**：MySQL `ENUM` 增删值需 `ALTER TABLE`，且与 ORM 映射繁琐 | — |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 存储略大 | `VARCHAR(32)` 比 `TINYINT` 占空间 | 可忽略（数据量小） |
| 索引略大 | 字符串索引比整数索引大 | 状态索引均与 `team_id` 组合，选择性可接受 |
| 拼写风险 | 字符串常量容易写错 | 应用层枚举 + `CHECK` 约束双重保证 |
| 无"合法转换"表达 | `CHECK` 只能校验取值，不能表达"A→B 是否合法" | 应用层状态机 + 状态守卫式 UPDATE（`DATABASE_CONSTRAINTS.md §4.4`） |

### 未来重新评估的触发条件

- 出现**海量状态行**且存储/索引开销成为可测量瓶颈；
- 需要**多语言状态标签**（可用展示层映射解决，不必改存储）；
- 数据库迁移到**不支持 `CHECK` 的版本**或引擎（则改为应用层强校验 + 二进制）；
- 状态数量膨胀到**需要独立字典表治理**（如状态带属性、可配置）。

## ADR-001-12：认证方案选择无状态 JWT

**状态**：Proposed（**推荐但待确认**，关联待决策 `DESIGN_BASIS §15 D-01`）

### 背景

需要确定认证方案。这与"是否引入 Redis"（`ADR-001-07`）强耦合。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 无状态 JWT**（推荐） | Access 2h + Refresh 7d；Refresh 存独立表（M2 决定存储位置） |
| **B. 服务端 Session（Redis）** | 引入 Redis 存 Session |
| **C. 服务端 Session（JDBC Session）** | Session 存数据库表 |
| **D. OAuth2/OIDC（第三方 IdP）** | 接入外部身份提供方 |

### 推荐方案

**方案 A（推荐但待确认）**：无状态 JWT，Access Token 有效期 **2h**，Refresh Token **7d**。Refresh Token 的存储位置在 **M2 决定**（对应 `D-01` 表述）。

> **必须标注**：本决策为 `DESIGN_BASIS.md §15 D-01` 的**推荐方案**，但 **`D-01` 尚未最终确认**。若 `D-01` 最终选择 Session，则本子决策状态转为 `Superseded`，并同步修订 `ADR-001-07`（Redis 决策）。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **无需 Redis**：无状态 JWT 不依赖服务端会话存储，与"首期不引入 Redis"（`D-07`）一致 | `D-01`、`D-07` |
| 2 | **水平扩展友好**：无状态便于未来多实例（虽然首期单实例） | — |
| 3 | **前端友好**：SPA 携带 Bearer Token 简单直接 | `TECH_STACK.md §1.1` |
| 4 | **SSOT 推荐**：`D-01` 推荐列为 JWT（无状态） | `DESIGN_BASIS.md §15` |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| **登出即时失效能力弱** | JWT 一旦签发，在有效期内难以即时撤销 | 短 Access TTL（2h）+ Refresh 撤销表；高风险操作可校验用户/团队状态 |
| 令牌泄露风险 | Token 被盗用则在有效期内可用 | HTTPS、短 TTL、Refresh 轮换、绑定用户状态校验 |
| 状态变更（禁用用户）延迟 | 禁用后旧 Token 仍可能在 TTL 内存活 | 每次请求校验 `UserStatus` 与 `TeamStatus`（返回 `AUTH-1003` / `TEAM-2002`） |
| 密钥管理 | `JWT_SECRET` 泄露影响全局 | 密钥存环境变量、不入库不入仓；定期轮换 |

### 未来重新评估的触发条件

- `D-01` 最终选择 Session 方案（则本子决策被取代）；
- 出现**强合规要求**（如需即时全局登出、会话审计、单点登录）；
- 需要接入**第三方身份源**（如企业 SSO、OAuth2/OIDC）；
- Token 撤销成为高频需求，短 TTL 无法满足；
- 多设备/多端登录管理需求上升。

## ADR-001-13：数量与金额用 DECIMAL/Decimal 并约定 JSON 传输格式

**状态**：Proposed

### 背景

数量与金额跨 **Java（`BigDecimal`）↔ JSON ↔ Python（`Decimal`）** 传输。若用浮点，会出现精度漂移，导致"算出来和存进去不一致"。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 全链路 `DECIMAL`/`BigDecimal`/`Decimal` + JSON 字符串/定标数字**（推荐） | 数据库 `DECIMAL`，两端精确类型，JSON 传字符串或定标数字 |
| **B. 用 `double`/`float` + 容差比较** | 简单但有精度误差 |
| **C. 以"分/毫"为单位存整数** | 整数存储，避免小数 |
| **D. 用字符串存一切数值** | 完全避免数值类型 |

### 推荐方案

**方案 A**（SSOT 已定，`DESIGN_BASIS.md §14.2`）：

| 用途 | 类型 | 精度 |
| --- | --- | --- |
| 数量（库存/销售/采购） | `DECIMAL(18,3)` | 3 位小数（支持拆零） |
| 单价 | `DECIMAL(18,4)` | 4 位小数 |
| 金额 | `DECIMAL(18,2)` | 2 位小数 |
| 计算中间量 | 保留 4 位小数，最终按目标精度四舍五入 | 保证可复现 |

**JSON 传输约定**：

- 数值字段以**字符串形式**（如 `"12.500"`）或**定标数字**传输，由契约明确；**禁止**依赖浮点 `number` 做精确运算。
- Java 侧 `BigDecimal` 序列化为字符串，避免 `double` 中间态；Python 侧用 `Decimal` 解析。
- **禁止 `FLOAT`/`DOUBLE` 存储金额与数量**（`§14.2`）。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **精度可复现**：确定性算法要求结果可复现（通用原则 G8），浮点会破坏这一点 | `§14.2` |
| 2 | **跨语言一致**：Java `BigDecimal` 与 Python `Decimal` 语义一致，避免两端算出不同结果 | `AI_SERVICE_CONTRACT.md §数值一致性` |
| 3 | **符合业务**：库存可拆零（0.001），金额仅两位 | `§14.2` |
| 4 | **避免容差比较的陷阱**：容差比较会掩盖真实不一致 | — |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 前端处理不便 | JS `number` 不精确 | 前端展示用字符串；精确计算由后端完成 |
| 比较需注意 scale | `BigDecimal.equals` 区分 scale | 统一用 `compareTo`（`CODING_STANDARDS.md §3.3 B2`） |
| 除法需显式舍入 | 无参 `divide` 可能抛异常 | 显式 scale + `RoundingMode.HALF_UP`（`§3.3 B3`） |
| pandas 默认 float | 计算中间态可能引入浮点 | 进入计算层前转 `Decimal`，输出前按 `§14.2` 量化（`CODING_STANDARDS.md §4.4`） |

### 未来重新评估的触发条件

- 业务出现**更高精度**需求（如 > 4 位小数）；
- 出现**跨币种/汇率**需求（当前 Out of Scope，`§2.1`）；
- 契约层发现 JSON 数值传输方式在**性能或兼容性**上成为问题；
- 引入需要**浮点友好**的新计算库且必须改变传输格式。

## ADR-001-14：`analysis_items` 与 `replenishment_items` 分离

**状态**：Proposed

### 背景

分析会产生"每个 SKU 的补货量"。疑问：是否把"计算快照"与"可审核的业务建议"放在**同一张表**，减少一张表与一次同步？

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 分离**（推荐）：`analysis_items`（不可变快照）+ `replenishment_items`（有状态业务对象） | 快照只读，建议有状态机 |
| **B. 合并为一张表** | 快照字段与状态字段同表 |
| **C. 只用 `analysis_items`**：建议状态直接记在快照上 | 快照变成可变 |
| **D. 只用 `replenishment_items`**：不保留快照 | 无法追溯"当时怎么算的" |

### 推荐方案

**方案 A**（SSOT 已定，`DESIGN_BASIS.md §3.1 第 1 条`）。

| 对象 | 性质 | 说明 |
| --- | --- | --- |
| `analysis_items` | **计算事实快照，不可变** | 记录"当时为什么这么算"（`D`/`IP`/风险/`Q_base`/`Q_suggest` 及算法版本） |
| `replenishment_items` | **业务对象，有状态** | 有状态机、可被人工改量、可审核、可被采购引用；必须引用来源快照 `source_analysis_item_id` |

**关键点**：一条建议必须引用其来源分析明细，但**两者数量可以不同**（人工改过）。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **可追溯性**：快照不可变，保证历史可复现；建议可改量，若合并则"改量"会破坏快照的不可变性 | `§3.1 第 1 条` |
| 2 | **职责清晰**：快照属于分析事实，建议属于业务流转；两者的生命周期与访问模式完全不同 | `MODULE_BOUNDARIES.md §2.7/§2.8` |
| 3 | **状态机独立**：建议有 `ReplenishmentItemStatus` 状态机与审核记录；快照无状态 | `§9.11` |
| 4 | **历史对比**：不同 run 的快照并存（`uk_ai_run_sku_wh`），支持"某 SKU 的历史 `D`/`IP` 趋势" | `DATABASE_CONSTRAINTS.md §3.2 #35` |
| 5 | **避免覆盖**：多轮分析产生多份快照；建议通过 `source_analysis_item_id` 关联，而不是覆盖历史 | `§3.1 第 1 条` |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 表数量增加 | 多一张表与一次关联 | 表数量可控（22 张）；关联通过 `source_analysis_item_id` 索引 |
| 数据冗余 | 建议中会冗余部分快照字段 | 冗余是"快照语义"所需（保留当时值） |
| 需保证一致性 | 建议生成与快照落库需同事务 | 结果落库 + 派发建议在同一事务（`MODULE_BOUNDARIES.md §2.7`） |
| 关联入口归属 | "由快照生成建议"的编排入口需明确 | 由 `replenishment` 侧编排（`MODULE_BOUNDARIES.md §8.2 E-2`） |

### 未来重新评估的触发条件

- 快照数据量增长到**存储/查询压力显著**，需要归档策略（不等于合并表）；
- 业务需要**频繁基于快照做复杂关系查询**导致双表 JOIN 成为瓶颈；
- 出现**"快照可被修正"**的合规需求（当前明确不可变）；
- 分析结果模型发生**结构性变化**（如引入多版本模型输出）。

## ADR-001-15：Python 侧为线性 Workflow 而非 Agent 自主循环

**状态**：Proposed

### 背景

Python 侧需要完成后处理编排。可选"显式线性 Workflow"或"Agent（Tool Calling）自主迭代"。

### 可选方案

| 方案 | 说明 |
| --- | --- |
| **A. 线性 Workflow（固定步骤顺序）**（推荐） | `validate → stats → rules → replenishment → llm`，步骤确定 |
| **B. Agent 自主循环（Tool Calling）** | LLM 自主选择工具、迭代直到收敛 |
| **C. 混合（关键步骤固定，解释步骤 Agent 化）** | 规则固定，LLM 可选用工具 |
| **D. 多 Agent 协作** | 多个 Agent 分工协作 |

### 推荐方案

**方案 A**：**线性、确定的 Workflow**，不启用 Tool Calling 自主迭代。

### 推荐理由

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **LLM 不参与任何判定**：判定（风险/补货）完全由确定性规则完成；LLM 只在最后生成解释 | `DESIGN_BASIS.md §11` 开篇 |
| 2 | **可控可测**：固定步骤可写 golden cases 精确断言；Agent 自主循环的行为不确定、难测试 | `TEST_STRATEGY.md §9/§11` |
| 3 | **成本与延迟可控**：Agent 循环会产生不确定次数的模型调用，成本与延迟不可预测 | `TECH_STACK.md §1.3.1` |
| 4 | **可解释与可审计**：每一步的输入输出都明确，便于追溯"当时怎么算的" | `§3.1 第 1 条` |
| 5 | **失败隔离**：LLM 是最后一步，失败不影响规则结果（`DEGRADED`） | `§9.7` |
| 6 | **不引入 Multi-Agent**：SSOT Out of Scope 明确不做 | `§2.1` |

### 代价与风险

| 代价/风险 | 说明 | 缓解 |
| --- | --- | --- |
| 缺乏自适应能力 | 无法根据中间结果动态调整步骤 | 首期步骤固定已满足需求；需要时按 `ADR-001-06` 重评 |
| 扩展新步骤需改代码 | 新增步骤要改 pipeline | 编排层已隔离，改动集中 |
| 无法利用 LLM 的"推理链" | 复杂分析可能受益于迭代 | 首期明确不做；以确定性换取可控 |

### 未来重新评估的触发条件

- 出现**必须由 LLM 自主规划步骤**的真实业务需求（如多源数据探查）；
- 需要**工具调用**（如让 LLM 主动查询补充数据）且能保证可测试与可审计；
- 出现**多步骤条件分支**的复杂分析流程；
- 行业实践与工具体系成熟到**可测试、可解释**地支持 Agent 循环。

| ADR-001-07 不引入 Redis | ① 多实例部署使内存态/local 锁不足；② 读压力使 MySQL 成为瓶颈；③ 需分布式锁或真正队列语义；④ 需网关级限流/熔断；⑤ 引入 MQ 需要配套 |
| ADR-001-08 状态与失败恢复 | ① 分析任务量/并发显著上升使轮询成为负担；② 需实时推送或任务优先级调度；③ 需可靠投递与死信；④ 引入 MQ 后重估状态权威 |
| ADR-001-09 一致性保障 | ① 需分库分表/跨库写入；② 出现跨服务事务；③ 引入 MQ 采用最终一致 + 补偿；④ 单库写入成为瓶颈且无法通过索引/批处理解决 |
| ADR-001-10 MyBatis-Plus | ① 出现极复杂对象图持久化需求；② MyBatis-Plus 与 Spring Boot starter 长期不兼容；③ 团队转向 JPA；④ 需跨数据库方言 |
| ADR-001-11 字符串枚举 | ① 海量状态行使存储/索引成为可测量瓶颈；② 需多语言状态标签（可用展示层解决）；③ 迁移到不支持 `CHECK` 的引擎；④ 状态数量膨胀需字典表治理 |
| ADR-001-12 无状态 JWT | ① `D-01` 最终选 Session（则被取代）；② 出现强合规要求（即时全局登出/会话审计/SSO）；③ 需接入第三方身份源；④ Token 撤销成为高频需求；⑤ 多设备登录管理需求上升 |
| ADR-001-13 DECIMAL/Decimal | ① 出现更高精度需求；② 出现跨币种/汇率需求；③ JSON 数值传输在性能/兼容性上成为问题；④ 引入需浮点友好的新计算库 |
| ADR-001-14 快照与建议分离 | ① 快照数据量需归档（不等于合并表）；② 双表 JOIN 成为瓶颈；③ 出现"快照可被修正"的合规需求；④ 分析结果模型结构性变化 |
| ADR-001-15 线性 Workflow | ① 需 LLM 自主规划步骤；② 需工具调用且保证可测试/可审计；③ 出现多步骤条件分支；④ 行业实践成熟到可测试、可解释地支持 Agent 循环 |
| **全局（技术基线）** | Spring Boot 基线的 OSS 支持窗口问题（`TECH_STACK.md §3.2` 的**强制评审项**，关联建议编号"（编号待 SSOT 统一，见 `DESIGN_REVIEW.md`）"）；MySQL 基线的生命周期评估；任何主版本升级均需 ADR |
