# ADR-004：审计写入的提交粒度、写入时机与批量入口

- **状态**：Accepted
- **日期**：2026-10-17
- **决策人**：项目负责人（项目方 2026-10-17 批准 `B4-PERF` 立项时授权）
- **关联**：`DESIGN_REVIEW` §5.1（NFR-PERF-02 复核）、**R42**（性能归因）、**R45**（孤儿审计）、**R47**（证据可复现）、**R48**（导入更新路径缺审计）；`MODULE_BOUNDARIES §2.10`；`DATABASE_DESIGN §6-J.4`；`DESIGN_BASIS §9.17`；`IMPORT_WORKFLOW §8.5`

---

## 1. 背景与问题

### 1.1 现状实现

`CatalogWriteService.recordMasterData` → `AuditWriteService.record` → `AuditLogWriter.insert`，后者标注 `@Transactional(propagation = REQUIRES_NEW)`。**每次审计写 = 一次独立提交**（挂起业务事务 → 新事务 → commit → 恢复）。

### 1.2 实测代价

`1` 万行导入（全为新建，故产生 `1` 万条 `MASTER_DATA_STATUS_CHANGE`）真栈实测 **180.3 s**；入库探针（`backend-java/tools/perf-probe/`）三段分解：

| 口径 | 1 万行 | 每行 |
| --- | --- | --- |
| 业务落库（无审计） | 23.2 s | 2.32 ms |
| 业务 + 审计**逐条**独立提交 | 108.2 s | 10.82 ms |
| 业务 + 审计**按批**独立提交（500 条/事务，审计仍 1 万条） | 30.8 s | 3.08 ms |

即：**提交粒度**贡献约 `77 s`（108.2 → 30.8），其余为业务与框架侧开销。`NFR-PERF-02`（1 万行 < 60 s）在现状下不可达。

### 1.3 两个衍生缺陷（与本 ADR 同批修复）

- **R45 孤儿审计**：`REQUIRES_NEW` 使审计在业务批**未提交**时就落库并提交；该批随后因非业务异常整批回滚时，审计**不回滚**，留下「记录为成功、数据不存在」的行。`PURCHASING_WORKFLOW` 已把此类记录命名为孤儿审计并要求规避。
- **R48 导入更新路径无审计**：四个 `updateXxx(Long id, JsonNode)` 私有方法**不写审计**，更新审计依赖 Controller 上的 `@Audited`（切点为 `@annotation(audited)`，见 `AuditAspect:59`）。导入经 `ImportConfirmService → CatalogWriteService.upsertXxxByCode → updateXxx`，**完全绕开 Controller 与切面** ⇒ 「库内已存在的编码」走 upsert 更新时**一条审计也不产生**，违反 `DESIGN_BASIS §9.17` L524「`MASTER_DATA_STATUS_CHANGE` 覆盖主数据的**创建/更新**/停用/启用」。

### 1.4 文档实际允许什么（关键，勿凭印象引用）

- `MODULE_BOUNDARIES §2.10`「关键事务边界」原文：审计写入**默认与业务事务解耦（独立事务）**，避免审计失败阻塞业务；高危操作（库存调整、审批、确认到货、取消采购单）**要求审计与业务同事务或在业务提交后立即写入并可补偿**。→ **未出现"每条一次提交"这一粒度要求**。
- `DATABASE_DESIGN §6-J.4`「事务保护」原文：审计写入使用**独立事务（`REQUIRES_NEW`）或在业务事务末尾追加**；禁止在只读事务中写入。→ **两者皆可**。

结论：**"审计条数"与"提交粒度"在规范上可分离**，后者是实现选择而非契约要求。

## 2. 决策

### D1　新增批量入口，不改既有单条语义

`audit` 模块新增：

- `AuditWriteService.recordAll(List<AuditEvent> events)`——与 `record` 同等的「永不抛异常」兜底；
- `AuditLogWriter.insertAll(List<AuditLogEntity> entities)`——在**一个** `REQUIRES_NEW` 事务中批量写入（多行 `INSERT` 或 MyBatis `ExecutorType.BATCH`），**一次提交**。

`record(event)` 的既有行为（未开启延迟写入时立即写）**不得改变**——REST / AOP 路径零影响。

### D2　写入时机：业务事务提交后批量写（延迟写入）

- 新增线程级 `AuditBuffer` + 可关闭的作用域（`AuditBufferScope`），由**业务方显式开启**（导入的每个批次事务各开一次）。
- 作用域内且事务活跃时，`record(event)` 不再落库，改为**入缓冲**；`occurred_at` 在**入缓冲时**取事实发生时刻（**不是**写入时刻，保证时间语义不变）。
- 事务同步回调：
  - `afterCommit` → 一次性 `recordAll(buffer)`；
  - `afterCompletion(STATUS_ROLLED_BACK)` → **丢弃**缓冲（不写）。
- 作用域关闭时缓冲**必须为空**；若非空（事务既未提交也未回滚的编程错误）→ 记 ERROR 日志并立即 `recordAll` 兜底，**不得静默丢弃**。

> 该设计同时满足 `§2.10` 的两种许可：审计写入仍**独立于业务事务**（`REQUIRES_NEW`），且时机上落在「业务提交后立即写入」。

### D3　审计条数不减少（红线）

禁止任何形式的**抑制 / 采样 / 合并 / 降级为批汇总**。`DESIGN_BASIS §9.17` 要求覆盖创建/更新/停用/启用 ⇒ 1 万行新建 = 1 万条；1 万行更新 = 1 万条（见 D4）。

### D4　补齐导入更新路径的审计（R48）

`upsertXxxByCode` 的**更新分支**必须产生一条 `MASTER_DATA_STATUS_CHANGE`（`change_summary` 需能区分「导入更新」与「导入新建」）。不得依赖 Controller 切面（导入不经 Controller）。REST 的 `PUT` 路径继续由 `@Audited` 记录，**不得因此产生重复审计**。

### D5　行级原子性：两遍式落库（去逐行 `SAVEPOINT`）

现状每行一次 `NESTED`（`SAVEPOINT` + `RELEASE`，两次往返）。改为：

- **Pass 1（正常路径）**：整批在**一个事务**内逐行落库，行内**不建立 `SAVEPOINT`**（catalog 提供批量入口，传播 `REQUIRED` 加入批次事务；异常**直接上抛，不得在事务内捕获后继续**，否则 `rollback-only` 污染）。
- **Pass 2（仅当 Pass 1 抛行级异常时）**：批次事务回滚后**逐行重放**（每行一个独立事务，失败行隔离、成功行照常提交）。
- 非业务异常（`C2`）**不进入** Pass 2，沿用「整批回滚 + 整批行记失败」语义。
- 两遍式必须满足不变式 `success_rows + failed_rows = total_rows`；Pass 1 的缓冲审计随回滚丢弃，**不得**因重放产生重复审计。

### D6　失败与回滚的语义（验收口径）

| 场景 | 数据 | 审计 |
| --- | --- | --- |
| 批次全部成功 | 500 行落库 | **500 条** |
| 批内 1 行业务失败 | 499 行落库 + 1 条行级错误 | **499 条**（失败行不产生审计） |
| 批内非业务异常（`C2`） | 整批回滚 | **0 条**（旧实现会留 500 条孤儿审计） |
| `recordAll` 写入失败 | 业务不受影响 | 记 ERROR（含条数与 action 分布）作为补偿线索 |

## 3. 备选方案与被否原因

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| A. 维持逐条 `REQUIRES_NEW`，只调业务批大小 | ❌ 否 | 提交粒度决定下限，调批大小无法抵消 1 万次提交 |
| B. 行级审计合并为「每批一条汇总」 | ❌ 否 | 违反 §9.17（条数减少、丢失单对象追溯能力） |
| C. 审计与业务**同事务**（J.4 的另一选项） | ❌ 否 | 审计写失败将回滚业务，违反 §2.10「避免审计失败阻塞业务」；且长事务持锁 |
| D. 异步线程池写审计 | ❌ 否 | 引入并发/丢失/线程上下文（`TeamContext`、`requestId`）丢失风险；首期无异步（`R7`） |
| **E. 延迟到提交后批量写（本 ADR）** | ✅ 采纳 | 条数不变、粒度大幅降低、顺带消除孤儿审计，且完全落在文档许可范围内 |

---

## 4. 影响

- **性能**：探针口径下 108.2 s → 30.8 s；真栈预计 180 s → 约 100 s 量级，**仍需** B4-PERF 的其余优化（框架侧开销）才能达到 60 s，见 `DESIGN_REVIEW §5.2`。
- **语义（改善）**：审计行与「已提交事实」一一对应；回滚不再产生「成功」记录。
- **风险**：`afterCommit` 与随后进程崩溃之间存在**丢失窗口**（旧实现无此窗口，但旧实现有孤儿窗口）。首期接受：错误仅记录 ERROR 日志；若后续要求强一致，可评估本地 WAL / 补偿任务（不在首期范围）。
- **兼容性**：未开启延迟写入的作用域时，`record` 行为逐字节不变。

---

## 5. 不改变的部分

- `audit` 模块仍**不依赖任何业务模块**（`§2.10`）。
- `AuditLogMapper` 仍只暴露 `insert` 与只读查询，不生成 `updateById`/`deleteById`（`DATABASE_DESIGN §6-J.4`）。
- 脱敏仍由 `audit` 模块集中完成（`AuditSanitizer`），业务方只传业务对象。
- 审计写入失败仍**永不冒泡**到业务。

---

## 6. 落地要求（由 `B4-PERF` 任务书约束）

1. 先落 `audit` 模块（D1/D2），`verify` 全绿后再改调用方；不得一次性改穿三层。
2. 性能结论必须由**入库脚本**复现（`backend-java/tools/perf-probe/` 为基线工具），不得再出现「探针在临时目录」。
3. `NFR-PERF-02` 阈值（1 万行 < 60 s）**不放宽**；两轮不达标按 `DESIGN_REVIEW §5.1` 裁定第 4 条处理（须项目方书面批准方可改口径）。
4. 审计条数须用 SQL 计数断言，**不得只测耗时**。
