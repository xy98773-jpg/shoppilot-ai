## 结论

`RB96_CHECK_TOTAL=65`、`RB96_FAIL_COUNT=0`、`RB96_NOTE_COUNT=2`。

- **`R74` 修复成立**：`P1`/`P5` 差额 0 全程无头；`P2`/`P3`/`P6` 三类真重放均带头。
- **无反向误杀**：判据收紧为 `replayed()` 后，真重放没有被误伤（`P2`/`P6`/`P3`）。
- **相邻面未被带走**：错误响应无头（`P7`）、同键异体仍 `INV-5003` 且无头（`P4`）、`R75` 未被顺手收紧（`P9`）。
- **`R76`（新发现，本批未引入）**：`P8` 实测 —— 首次差额 0 既不写流水也不落幂等记录
  （`inventory_transactions.idempotency_key` 是幂等键的**唯一载体**），余额被改后再发**同 key 同请求体**
  会**真落账**（`txn=5`、余额 `5.000 → 8.000`、流水 +1、`#12` +1），违反 `API_CONTRACT §6.3`
  「同幂等键 + 请求体一致 → 返回首次结果、**不重复执行**」。根因在 `B6` 的差额 0 分支，非 `B9.6` 引入，
  已登记 `R76` 待裁决（不阻塞 `B10`）。

## 方法论

开发 `W1–W3` 覆盖了「修复点本身」，但**未覆盖**：同键异体、同键重复无变更、`MANUAL_ADJUST` 通道、
错误响应、以及「无变更不落幂等记录」的连带后果。本轮 2 条 `NOTE` 全部来自**自加探针**，
与前几批（`R62` / `R68` / `R74`）同源：**复现对方的场景证明不了完整性**。

`Communications link failure`：前者是 fork 退出超时告警、后者是 `Testcontainers` 容器销毁后
